部署狀態：已完成非互動 SSH、pod 定位、health、接收程式安裝及真實訓練資料 dry-run；正式候選提交與全流程回測仍需第一個真實來源驗證。實際目前支援週期為 5m／15m／30m／1h／4h；下文的日線屬規劃，尚未支援。Skill 匯出包含操作手冊與脚本，不包含私鑰、密碼或完整 Webhook。既有較早段落的「尚未建立 Skill」是計畫初稿狀態，以上最新部署狀態優先。

建立可排程執行的「找 BTC 有效優質自動交易策略」Skill，配合 Python 研究與回測引擎，持續尋找規則明確、可以忠實實作、扣除成本後具研究價值的 BTC 策略。

本計畫的成果是可追查、可重現的研究流程與候選策略，不保證產生盈利策略。歷史研究合格與可投入實盤必須分開判定。

本階段包含來源搜尋、規格提取、程式生成與審查、多週期研究、分段回測、比較基準、結果記錄、Discord 通知及排程整合。實際下單、交易所帳戶串接、資金投入與實盤部署不在本階段範圍內。

本文件只是計畫書，不代表已建立 Skill、修改引擎或新增排程。

## 二、現況與問題

策略 1 已被標記為來源審查失敗：原策略只做多，生成程式加入沒有依據的做空與進出場規則；4 小時週期亦沒有策略本身的設定依據。已保存的回測數字只能用於檢查當時生成程式，不能代表原始策略績效。

目前主要瓶頸為：

1. 搜尋取得大量介紹頁、重複來源或不完整規則，轉成可用候選的比例低。
2. 來源處理偏重 Python 檔案，可能漏掉完整 Pine Script 或文章規格。
3. 大型程式檔案與相依函式定位不足。
4. 策略規格缺失時，模型可能補出不存在的规则。
5. 每個候選只使用一個指定週期，尚未形成獨立、可追蹤的週期變體研究。
6. 尚未完成比較基準、參數穩健性及試驗總數追蹤。

已完成的通知設定作為本計畫前提：Strategy Hunt 零候選也須通知；搜尋與回測使用各自 Webhook；兩個排程對頻道 1494372820380160100 的自動公告已停用。

## 三、設計原則

- Skill 定義操作流程、研究標準及判斷規則；Python 引擎負責確定性的資料處理與計算。
- 原始策略重現與研究變體分開存放，所有修改都可追查。
- 缺少規則必須揭露，禁止把模型補充的規則冒充來源設定。
- 每次嘗試與失敗都保留，不能只保存績效好的版本。
- 先通過來源與程式審查，再投入完整回測資源。
- 使用固定研究預算與預先定義的門檻，避免無限制搜尋參數。
- 歷史測試資料一旦參與挑選，就不再當成新的獨立驗證。
- 找不到合格策略是有效研究結果，不自動降低門檻。

## 四、完整執行流程

研究任務 → 假設選擇 → 來源搜尋與去重 → 規則提取 → 規格審查 → 程式生成 → 程式與訊號審查 → 回測 → 穩健性評估 → 結果記錄與通知 → 前向模擬候選。

### 4.1 研究任務與假設

每輪先確定研究問題，而非單純輪流搜尋指標名稱。第一版涵蓋趨勢突破、趨勢回調、均值回歸、波動收縮突破及簡單市場狀態切換。

任務須記錄：假設、適用市場、交易方向、允許週期、來源類型、查詢字串、模型與搜尋预算、Skill／引擎版本。

搜尋分配同時考慮來源可用率與驗證期績效。保留探索額度，避免少量結果使流程只研究某一個家族。解析失敗不計為策略績效失敗；找到程式也不計為盈利成功。

### 4.2 來源搜尋與處理

優先取得具體規則、公開實作及清楚設定，接受完整 Python、Pine Script、其他可轉換程式及規則完整的文章。其他市場的策略若移植到 BTC，必須標記為市場移植變體。

GitHub 來源保存網址、commit、檔案路徑及內容指紋。文章保存擷取時間與內容指紋。來源可用性與授權條件須在實作時確認。

大型檔案先定位策略類別、訊號函式、參數與相依函式，再擷取必要上下文；若無法完整理解相依關係則拒絕，不能靠截斷片段推測。

去重包含網址、來源內容、策略規格及訊號行為。相同來源進入冷卻期；再次處理必須有來源更新或解析能力改善等理由。

### 4.3 策略規格與來源審查

規格至少包含市場、合約類型、交易方向、週期、指標與參數、進場、出場、持倉限制、倉位大小、成交時點及風險規則。每個核心規則須指向來源證據。

審查重點包括：是否只做多或允許做空、是否重複加倉、訊號成立時間、退出條件、跨週期資料對齊、缺失參數及重繪可能性。

輸出分為「原始重現」「研究變體」「規則不足而拒絕」。來源未指定週期時只能建立研究變體，不能宣稱忠實重現某個指定週期。

### 4.4 實作與驗證

使用受限制的策略介面生成程式，禁止來源程式任意存取憑證、網路或主機。先確認語法、資料索引、暖機區間、訊號方向與持倉轉換。

以簡短人工可核對行情驗證具體交易行為；檢查未來資料引用、重繪、同根 K 線不合理成交及多週期資料提前可見問題。來源對照與程式執行檢查分開進行，模型文字宣稱「通過」不是唯一證據。

## 五、多週期與參數研究

第一版擬研究 15 分鐘、1 小時、4 小時及日線，但須先核實每個週期的歷史資料與引擎支援。資料不合格的週期不得執行績效比較。

來源有指定週期時先重現原週期；其他週期作為獨立變體。來源沒有指定週期時，預先列出少量週期研究任務。

每個家族設定候選、週期及參數試驗上限，開始前記錄预算。挑選使用訓練與驗證資料，最後測試資料不參與選擇。最佳參數附近亦須評估，避免只接受單一尖峰設定。

## 六、資料與回測設計

第一版沿用現有 BTCUSD_PERP 合約與 BTC 計價研究架構；必須核對反向合約損益、倉位與資金費用計算。若未來加入其他合約，另建任務及成本模型，不直接混合績效。

沿用既有時間分段作為初始配置：2020 年可用資料起點至 2023 年為訓練期，2024 年為驗證期，2025 年至最新完整資料為歷史測試期。實際起訖由資料快照決定，不假設具有完整 2020 年資料或完整 2026 年資料。

已看過的歷史測試結果屬研究用資料。任何新變體若因这些結果而調整，都須揭露；後續以前向資料提供新的驗證。

回測計入手續費、滑價、價差與適用的資金費用。成交依訊號可取得的時間安排，資料缺口、重複、時區與未完成 K 線均先檢查。成本提高至 1.5 倍作為壓力情境。

同時報告 BTC 累積淨報酬與 USD 組合表現。50% 門檻指 BTC 累積淨報酬，不是年化報酬。

### 6.1 第一版研究門檻

| 指標 | 門檻 |
|---|---|
| 驗證期與測試期累積淨報酬 | 各 ≥50% |
| 驗證期與測試期最大浮動回撤 | 各 ≤15% |
| 驗證期與測試期 Profit Factor | 各 ≥1.10 |
| 驗證期與測試期 Sharpe | 各 ≥0.5 |
| 驗證期與測試期交易次數 | 各 ≥30 筆 |
| 三個測試子區間 | 至少兩段正報酬 |
| 1.5 倍成本壓力 | 淨報酬 >0 |
| 來源與程式一致性 | 必須通過 |

低頻策略可能因交易次數不足被淘汰，需清楚標示「樣本不足」；不得自動放寬。其他週期門檻調整須另列政策版本，不能悄悄改變判定。

### 6.2 比較基準與穩健性

新增不交易、買入持有 BTC 及簡單固定規則趨勢基準，使用相同時間區間與可比較的成本條件。買入持有以 USD 表現呈現，BTC 本位策略同時報告 BTC 數量變化，不能直接把不同計價單位的百分比相減。

風險或曝險相近的比較若可實作則加入，否則明示缺失。第一版先報告基準差異；是否作為額外硬性淘汰門檻，在完成計算定義後決定。

檢查收益是否集中於少數交易、特定年份或行情，並評估參數附近表現與延後成交敏感度。保存所有已測試版本數量，揭露多次試驗造成的挑選偏誤。

## 十二、測試與驗收標準

1. 使用規則完整與不完整來源案例，確認提取與拒絕理由符合事實。
2. 使用策略 1 類型案例，確認不會擅自加入做空或把框架週期當成策略週期。
3. 核對人工可計算交易的訊號、損益、費用與資金費用。
4. 檢查資料時間對齊、未來資訊、重繪及多週期行為。
5. 固定規格與資料快照重新執行，得到一致結果。
6. 驗證資料庫重試不增加重複結果，且失敗可恢復。
7. 驗證搜尋零候選通知、回測結果通知與傳送失敗紀錄。
8. 核對兩個原排程仍啟用，並確認停用頻道不再產生自動公告。
9. 新舊引擎不並行處理同一候選，備份可用于回復。

驗收不要求一定出現 ≥50% 的策略；要求門檻判定正確、過程可追查與結果可信。研究成效另以來源可用率、忠實實作率、有效回測數、成本及歷史合格率持續衡量，不以候選數量單獨判定成功。

## 十三、主要風險與對策

| 風險 | 對策 |
|---|---|
| 大量試驗後偶然找到漂亮結果 | 保存全部試驗、限制预算、獨立測試與前向驗證 |
| 模型補規則或誤讀來源 | 來源證據、獨立審查、具體訊號案例 |
| 來源更新或消失 | commit／內容指紋與取得時間 |
| 不同合約與計價方式混淆 | 明確合約規格，BTC／USD 分開呈現 |
| 成本使高頻策略失效 | 現實成本、壓力情境與成交敏感度 |
| API 支出與排程堆積 | 每輪限額、鎖、逾時、佇列與監控 |
| Discord 通知漏發或重複 | HTTP 狀態記錄、事件唯一鍵與有限重試 |
